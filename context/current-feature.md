## Goals

<!-- Goals & requirements -->

- Build a custom `/sign-in` page replacing NextAuth's default: email + password fields, a "Sign in with GitHub" button, a link to `/register`, plus form validation and error display
- Build a custom `/register` page: name, email, password, confirm password, with validation (email format, passwords match), submitting to `/api/auth/register` and redirecting to sign-in on success
- Point NextAuth at the custom sign-in page so unauthenticated `/dashboard` traffic lands there instead of the built-in page
- Create a reusable avatar component: use the user's `image` (from GitHub) when present, otherwise render initials derived from the name ("Brad Traversy" → "BT")
- Replace the sidebar footer's mock `currentUser` with the real session user — avatar, name and email
- Add a dropdown on the sidebar avatar with a "Sign out" action, and make the avatar link to `/profile`

- Audit Quick Wins: ran a full read-only audit of the codebase (0 critical, 0 high, 1 medium, 2 low) and shipped the one finding that survived triage — parallelizing `prisma/seed.ts`. The script made ~30 sequential round trips: 7 system-type upserts, then a nested loop creating each collection followed by its items one at a time. Now the system types resolve in a single `Promise.all` (each has a distinct name, so they cannot collide with one another), system types and the demo user seed concurrently, all 5 collections go in one round, and all 18 items go in one *flattened* round rather than a collection's worth at a time — roughly 4 sequential rounds in total, bounded below that only by the driver adapter's connection pool. Two hazards came with the parallelism, and neither was in the original spec. First, `connectOrCreate` on the items' tags would race on `Tag.name`'s unique constraint the moment two concurrent writes shared a tag — and eleven of the seed's items do — so tags are now created up front with one `createMany({ skipDuplicates: true })` and the items `connect` to them, removing the race rather than retrying through it. Second, parallel writes meant Postgres no longer stamped `createdAt`/`updatedAt`/`addedAt` in source order, so the dashboard's Recent Items list and the collection grid — both ordered by recency — shuffled between seed runs; a `seedTimestamp(index, total)` helper now spaces rows a minute apart by source index off a single `SEED_START` captured once per run, so write order stops mattering. That the explicit `updatedAt` actually lands was verified directly against the database rather than assumed: Prisma does honour it on a `@updatedAt` field, and `db:test` orders collections by *name*, so it would not have caught the value being silently ignored. - Auth Setup (NextAuth + GitHub, phase 1 of 3): wired up NextAuth v5 (`next-auth@5.0.0-beta.32`) with `@auth/prisma-adapter@2.11.3` and GitHub OAuth, using the split config pattern. `src/auth.config.ts` holds the edge-safe half — `providers: [GitHub]` behind `satisfies NextAuthConfig`, nothing that touches the database — and `src/auth.ts` adds `PrismaAdapter(prisma)` plus `session: { strategy: "jwt" }` and exports `auth`/`handlers`/`signIn`/`signOut`. Next 16 runs proxy on the Node runtime, so the split is no longer strictly an edge-compatibility requirement, but importing `@/auth` there would pull Prisma and the Neon driver into a bundle that executes ahead of every dashboard request, and the JWT strategy means the cookie alone answers "is this person signed in".
